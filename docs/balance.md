# 数值怎么调：工具、流程和计划

套餐（肉鸽关卡）的战斗节奏、敌人安排和各种数值，靠三层工具来算、来模拟、来防止改坏。
当前只调**微辣**：中辣和变态辣在菜单上是锁着的，以后作为新关卡再开（`src/settings.js` 的 `openDifficulties`）。

- 现状的全部数字：[balance-report.md](balance-report.md)（生成文件）。
- 数值本身：`src/chinatown/runtune.js`（关卡）、`zombietune.js`（僵尸）、`loadout.js`（弹药）、`arsenal/src/data/`（武器、等级、状态）。
- 规则：`src/chinatown/runflow.js`。套餐的钟、一道菜怎么做、刷什么、击杀给多少镬气、掉什么弹药这些**纯规则**在这里，
  游戏（`run.js`）和模拟器用的是同一份代码，所以模拟的和实际玩的不会是两套规则。

## 一局怎么走：套餐的钟、三口灶、关底

- **套餐的钟**。`RUN.stages` 里每道菜的 `at` 不是街上的时间，是套餐的钟（`runflow.js` 的 `clockStep`）。
  灶上有菜、还在招尸的时候它和街上的时间一样快，其余时候只走 `RUN.simmer`（现在是一半）；
  走到一道菜的末尾就停下，等下一口灶起火。第 1、2、3 口灶起火，分别开始第 2、3、4 道菜。
- **三口灶是主线**，不再是可选的。一道菜是颠勺三次、每次颠完菜在灶上自己炒一段、最后打包（数值在 `RUN.stove`，规则是 `newDish` / `dishStep`）。
  颠勺和打包时双手占着，不能开火，可以走；每颠一下往面前喷一次火。颠完要把镬端回灶上才开始炒，炒的时候人去哪都行。
  对玩家的约束只有一条：到点要回灶。该颠勺或该打包了没人接手，过了 `burn` 秒菜就糊一次，每糊一次奖励降一档（`dishGrade`）；
  再放 `char` 秒就烧焦，只能打包，照样算一份外卖但没有奖励（`dishOf` 的 `charred`）。同一时间只能做一道。
  刷怪加快、同屏上限加高，都只在菜还在招尸时生效（`dishHot`：到第三段炒完为止），而且随三次颠勺逐级加码（`swell`）。
- **关底**在第三道菜打包后 `RUN.boss.after` 秒登场，和街上过了多久无关。不出完三道菜，一局不会结束。
- **定时的精英**还是按街上的时间来，但灶上有菜时不来，第三道菜出餐后也不再来；每道菜在第三段开炒时自带一只。

这对工具意味着：

- 报告第 2 节的「分钟」是套餐的钟。它落在一局的第几分钟要看玩家什么时候起灶，所以第 5 节有一张表，
  列出每种玩家起火、出餐、关底登场的时间（街上的时间），以及糊过多少、关底前升了几级。
- 一局多长不再是定死的 9 分钟，而是玩家起灶早晚的结果。`PROFILES` 里每种玩家的 `stoves`（什么时候去起每口灶）
  因此是最要紧的假设之一；做菜的手脚（接镬的反应、错过颠勺的概率、端镬回灶要多久）也在那里。
- 模拟有硬上限（`run.mjs` 的 `LIMIT`，20 分钟）：到时间还没结束的局记为「超时」，算输。不起满三口灶的玩家会落到这里。
- 护栏里原来按「9 分钟」算的，改成按实际发生的算：关底之前的升级次数，数到模拟里关底真正登场为止；
  敌人成长看的是关底前最后一道菜；另有一条「一局的长度」看普通玩家几分钟见到关底。

## 三层工具

| 层 | 是什么 | 多快 | 入口 |
| --- | --- | --- | --- |
| 1 数值表 | 由规则直接算：套餐的钟上每分钟刷多少、涌入多少血量、一道菜要多久、每把武器的持续输出和击杀时间 | 即时 | 报告第 2–4 节 |
| 2 整局模拟 | 不开画面，把一局从点主菜打到关底，每种玩家 100 局，固定随机种子 | 每局约 15 毫秒 | 报告第 5 节，`npm run balance:sim` |
| 3 真实代码实测 | 试验场用真正的武器代码考「清群」和「单体」两场（`arsenal/tools/balance.mjs` → `arsenal/scripts/balance.json`）；武器按它对标准线，模拟器拿它校准 | 六十个形态约 2 分钟 | 报告第 4、6 节 |

第 2 层是简化模型（`scripts/balance/engine.mjs` 开头写了它省略什么）：没有地图，瞄准是一个命中率，
**玩家水平是假设**（`scripts/balance/run.mjs` 的 `PROFILES`）。所以它能回答「改了之后变难还是变容易、差多少」，
还不能回答「真人通关率是多少」。后者要靠试玩，或者靠还没做的「真游戏里的机器人」来校准这些假设。

## 命令

```sh
npm run balance          # 重新生成 docs/balance-report.md
npm run balance:check    # 护栏 + 报告是否最新（npm run check 里已经包含）
npm run balance:sim 500  # 只跑整局模拟，每种玩家 500 局，打印到终端
node scripts/balance/lab.mjs                 # 只看模型和实测的对照
node scripts/balance/report.mjs --print      # 报告打印到终端，不写文件
```

## 改数值的流程

1. 改 `runtune.js` 等数值文件（规则要变就改 `runflow.js`，游戏和模拟器一起变）。
2. `npm run balance`，看报告的差异：护栏有没有从「未达标」变成「达标」，别的行有没有被带坏。
3. 把报告和数值一起提交。报告不是最新的话 `npm run check` 会失败，所以 PR 里一定能看到这次改动对数字的影响。
4. 改了武器本身（`arsenal/`）先重新实测：`node arsenal/tools/balance.mjs --seconds 120 --write`，再 `npm run balance`
   和 `node arsenal/scripts/design-doc.mjs`。只想看某几把：`--only shotgun,crossbow`（不加 `--write` 只打印）。
   这个工具会开一个不显示窗口的浏览器跑试验场的测试台（不是游戏，不锁鼠标）。**别的会话的试验场开在 5311 端口时它会直接用那一个**，
   量到的就是别人的代码：自己在工作目录里另起一个（`npx vite --config arsenal/vite.config.js --port 5321 --strictPort`），
   再用 `ARSENAL_URL=http://127.0.0.1:5321/` 指过去。
5. 最后还是要真人玩：模拟看不出手感。试玩结论和报告对不上时，改的是 `PROFILES` 里的玩家假设，不是去凑数值。

## 武器的统一标准

十二把试验场武器的每个形态（1 级、3 级甲乙、5 级甲乙，共六十个）都考同一场试，对同一条**标准线**。
怎么考写在 `arsenal/tools/balance.mjs` 开头，标准线和总分的算法在 `scripts/balance/data.mjs`（`LINE`、`score`），
目标带在 `scripts/balance/guards.mjs`（`WEAPON_BANDS`），现在的成绩在报告第 4 节。

- **清群**：十六只（十三只行尸、三只重型）在 16–30 米外冒出来、倒下就补，一半的行尸会跑。机器人瞄最近的一只，够得着才开火，
  够不着就迎上去（所以近战和短射程不吃亏）。每分钟打倒 69 只记 1 分。
- **单体**：面前站一只精英，倒下立刻换一只。每秒 138 伤害记 1 分，含换弹。这一项代表打精英和关底。
- 两项相加是**总分**。标准线是定下来不动的（划线时十把吃弹药的枪 1 级的中位数）：以后是武器去对线，不是线跟着武器走。

定下来的几条（护栏会拦，想改先改 `WEAPON_BANDS` 并在这里写明原因）：

| 规则 | 数字 | 为什么 |
| --- | --- | --- |
| 1 级吃弹药的枪，总分在标准线上下 | 1.75–2.45 | 开局拿到哪把都能打；可以偏科（电弧枪清群 1.4、单体 0.6），总分不能偏 |
| 3 级每条岔路 | 2.6–3.7 | 岔路是换打法，不是谁比谁强一截 |
| 5 级每条岔路 | 3.5–4.9 | 5 级大约是 1 级的两倍；再叠三层调料还能翻一倍多，不需要更高 |
| 同一把武器 5 级的两条岔路相差 | ≤ 25% | 两条都值得选 |
| 1 级时一池弹药打倒的数量 | 45–70 只 | 四种弹药掉落是均等的，所以一池弹药对每把枪要值同样多；一发打得多的，一发就贵（`loadout.js` 的 `ARMS.per`） |
| 不用弹药的武器（敕令、金钱剑、青龙）不高过吃弹药的 | 5 级 3.7–4.2 | 不然「弹药必须捡」就没有意义。这条没写成护栏，调的时候看一眼报告 |

量出来的东西和它的局限：

- 机器人不会打偏身体、不会后退、不会走位，受伤数比真人高得多，只用来看「压不压得住」。瞄头的三把按 60% 的时间瞄在头上算。
- 清群那场每分钟 150 只左右就到顶了（僵尸补不过来），5 级里清群特别强的形态之间分不出高低。
- 游戏自带的卡宾枪和手枪不在试验场里，量不了；它们只按等级表成长。
- 僵尸从哪儿冒出来是随机的：同一份代码重复量，清群那一项有一成以内的浮动（单体几乎不动），目标带两边各留了这么多余量。
  量出来贴着带边的形态，先调开一点再写入。

## 护栏

目标写成了规则（`scripts/balance/guards.mjs`），列在报告第 1 节。

- **已启用**：现在成立、以后也必须成立，不满足时 `npm run check` 失败。
- **待启用**：计划里要达到、现在还没达到的，只报告。哪次改动达到了，就在那次改动里把它的 `enforce` 改成 `true`。

## 计划

用户定下的四条不动：弹药必须捡、弹药分四种、武器不限数量、红包只升手上那把。

| 步 | 改什么 | 对应的护栏 |
| --- | --- | --- |
| 0 地基（已完成） | 规则抽成 `runflow.js`，三层工具，基线报告；锁上中辣和变态辣 | 已启用的三条 |
| 1a 安静的街（已完成） | 开局游走的行尸；不自动回血，击杀掉外卖盒；换一次弹装满全部；补给箱标记走近才显示 | — |
| 1b 三口灶（已完成第二版） | 警报器换成大排档的灶，灶成了主线：起一口灶开始下一道菜，颠勺三次、每次颠完自己炒一段、打包出餐拿奖励，到点不回灶会糊；第三道菜打包后关底登场。什么时候起由玩家定，一局多长也就由玩家定 | 一局的长度 |
| 1c 节奏和成长 | 升级减到 10 次左右、第一次推后；行尸和重型随时间变强；修胀尸占比；每道菜的起伏 | 升级的三条、胀尸占比、敌人成长、每道菜有起伏 |
| 2 敌人（已完成第一版） | 靶场试用的模型里取了五个：关底、两种精英（血厚的和追人的「猎手」）、胀尸各有专门的模型；新增三只一群的快尸 | 专精和全用都走得通 |
| 3a 武器（已完成第一版） | 十二把武器六十个形态对同一条标准线，一池弹药对每把枪值同样多（见上面「武器的统一标准」） | 武器的五条、武器成长不失控 |
| 3b 弹药的松紧 | 掉落和补给箱给多少。等有了试玩或游玩日志的数据再调：补给箱现在没有导航标记，真人拿到的会比模拟少 | 专精要为弹药奔波 |
| 4 关底 | 分阶段变招，血量用模拟重新定 | 通关率（校准后） |

## 还没做的

- **真游戏里的机器人**：让机器人在真实游戏里打完整局，用来校准 `PROFILES`。在它或足够的试玩数据到位之前，
  报告里的通关率只看相对变化。
- **卡宾枪和手枪对标准线**：它们是原版的枪，试验场里没有，现在只能按纸面数字估（卡宾枪和蜂巢相当，手枪约为卡宾枪的七成）。
- **游玩日志**：每把武器的持有时长、击杀和耗弹已经在记（[telemetry.md](telemetry.md)），攒够了可以拿来对照这套标准。
- 敏感度分析（每个数值各调 ±20% 看影响）和按目标反推数值，等第 1 步有了要调的旋钮再加。
- 手机的尸群规模，模拟器支持（`simulateRun({ device: "phone" })`），报告里还没有单列。
